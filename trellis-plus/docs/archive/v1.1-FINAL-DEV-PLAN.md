## 1. 目标与范围

### 1.1 用户的四个原始问题（不变）

1. `prd/design/implement.md` 颗粒度不够，难以 review；2. 不强制 Service/Controller 写单测；3. 缺少 subagent 审查 design/implement；4. 缺少 alibaba/open-code-review（ocr）步骤。技术栈 Java 8 + Maven + JUnit5 + Mockito；在 `trellis init --opencode` 之后用 Node 脚本增强，脚本接收项目路径，不需预先复制进项目。【交接文档 §1.1】

### 1.2 v1.1 目标（用户已确认 P0+P1 全做，P2 不做）【交接文档 §1.3】

| # | 级别 | 目标 | 验收 |
|---|---|---|---|
| P0-1 | 必须 | git pre-commit hook 提交时硬兜底 | AI 绕过 2.4/2.5 直接提交，缺测试/OCR 未分诊 → 被拦 |
| P0-2 | 必须 | `--patch-agents`：implement/check 子代理加测试规范托管块 | 轻量任务里的实现子代理也被要求写单测 |
| P0-3 | 必须 | 轻量任务拦截 | 标 lightweight 却改了 Service/Controller → `test`/`pre-commit` 失败 |
| P1-4 | 重要 | OCR 门禁：版本检查 + severity 感知分诊 + 任务背景 | critical/high 不可 deferred；误报要代码证据；ocr<1.9.0 报错；带 `--background-file` |
| P1-5 | 重要 | 设计模板 9 章 + reviewer 增强 | 含数据模型/事务并发异常；隐含假设、反向验收、高引用数 |
| P1-6 | 重要 | `REQ→DES→IMP→TEST` 稳定编号链 | gate 校验整条链，缺环报具体错误 |

P2（不做）：Maven 多模块按 `pom.xml` 定位模块跑测试；步骤 1.1 加深度指针；`--install-ocr`。

### 1.3 本会话新增需求 N-1：支持用户的 drill-me 工作流

用户原话：开发习惯是**先用 drill-me skill 分析需求内容、深入阅读代码，跟我对齐需求问题，然后再进行开发设计**；希望 trellis-plus 也支持这个工作流。

落地为：新增**步骤 1.8 需求对齐**（在 design 之前），产物 `alignment.md`，由确定性门禁校验，并与设计/审查/硬门禁联动。设计详见第 4 节。

## 4. 新增需求设计：drill-me 需求对齐阶段（步骤 1.8）

### 4.1 需求理解与假设

用户的习惯流程：`drill-me` 分析需求 → **先读代码** → 与用户**逐点对齐** → 才做开发设计。

> **关键假设（【未验证】，第 9 节 NEEDS-USER U-1）**：我**没有看到** `drill-me` skill 的内容。我按其名称与描述假设它是"对用户做访谈式追问、直到共识"的交互 skill。因此设计成**与具体 skill 内容解耦**：访谈由 `drill-me` 自己的指令驱动；trellis-plus 只提供**记录契约 + 校验 + 联动**，并带一份内置兜底协议（`plus-align`）。若 `drill-me` 实际行为不同，只需调整 `plus-align` 的文案与 1.8 步骤措辞，gate 不变。

### 4.3 新的 Phase 1 流程

```
1.0 create
```

### 4.4 `alignment.md` 规范与校验规则（`gate align`，`alignGate()`）

文件结构（模板见 `assets/plus/templates/alignment.md`）：头部 `Status: IN-PROGRESS|ALIGNED`；`## 1. Understanding`、`## 2. Code Findings`、`## 3. Questions & Decisions`、`## 4. Open Questions`、`## 5. Out of Scope`。

### 4.5 gate 能证明什么、不能证明什么

- **能**：记录完整、引用的代码真实存在、内部一致（决策↔文档）、顺序被物理约束（seed 分阶段 + pre-start）。
- **不能**：证明用户**真的**回答了。`(user, <date>)` 是**审计线索**，AI 可以伪造。缓解：①`plus-align` 明确禁止为推测写 `(user…)`；②人工审阅 §1/§3/§4 与归属；③Reviewer `plus-req-coverage` 增加"决策是否被遵守、Out of Scope 是否被触碰"检查（【待做】）。这是该类机制的固有边界，**不应在 README 里夸大**。

### 4.6 与其他组件的联动

`seed`（分阶段）→ `align`/`lint-plan`（先 `alignGate` 再 `lintPlan`）→ `design-review`（哈希含 alignment）→ `pre-start`（硬门禁）；reviewer 读取 `alignment.md`（【待做】）；`design.md` 模板的 Assumptions 行可引用 `ALIGN-n` 作为 `CONFIRMED` 来源；面包屑 planning 首行即指向 1.8。

### 4.7 配置与选项

`plus.config.json`：`alignment.{required, minCodeFindings, minQuestions}`；安装器：`--align-skill <name>`（记入 manifest `options.alignSkill`，`doctor --fix` 沿用）。
