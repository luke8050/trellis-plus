# trellis-plus v3.0 使用说明

## 1. 前置条件

- 新项目不必先 `trellis init`：`install` 会用固定的 Trellis 0.6.17 替你完成；已 `trellis init` 的项目（OpenCode 平台）也可以直接 `install` 或 `apply`。项目应是 git 仓库（`install --git-init` 可代为初始化）。
- Node ≥ 18、python3 ≥ 3.9、git。
- 可选：`ocr`（alibaba/open-code-review）。没有或不可用时自动降级为委托模式。
- 单测门禁需要 Maven（Java 8 + JUnit5 + Mockito）。
- `/grill-me`、`grilling` 技能**可选**：装了澄清时用，没装就跳过（安装时不检查、不告警）。

## 2. 安装、升级与维护

### 2.1 一条命令安装（`install`）

```bash
npx @luke8050/trellis-plus install <项目目录> -u <你的名字>      # 装 Trellis 0.6.17 + trellis-plus
npx @luke8050/trellis-plus install <项目目录> --dry-run          # 只打印计划，不执行
```

依次：预检（Node ≥ 18、python3 ≥ 3.9、git）→ `trellis init --opencode -u <名字> -y`（固定 0.6.17；项目已有 `.trellis/` 和 `.opencode/` 时跳过）→ `apply --all` → `doctor`。幂等，可重复执行。

- `-u`：开发者名；缺省取环境变量 `TRELLIS_DEVELOPER`，再取 `git config user.name`。
- 已有项目的 Trellis 不是 0.6.17 时**拒绝**（补丁锚点依赖上游原文），`--allow-version` 可强行尝试。
- 内网 / 离线：`--trellis-pkg ./mindfoldhq-trellis-0.6.17.tgz`（先在有网机器 `npm pack @mindfoldhq/trellis@0.6.17`）。npm 源沿用你自己的 npm 配置。
- 目录不是 git 仓库时 pre-commit hook 会被跳过并提示；`--git-init` 先 `git init`。
- 固定的 Trellis 版本写在 `package.json` 的 `config.trellisVersion`（唯一来源）。

### 2.2 升级（`update`）

```bash
npx @luke8050/trellis-plus@latest update <项目目录>             # npx 会缓存旧版本，务必带 @latest
npx @luke8050/trellis-plus@latest update <项目目录> --dry-run
```

流程：预检 → 把受保护文件复制到 `.trellis/plus/backup/<时间>/protected/` → 固定版本的 `trellis update --force`（项目版本落后时加 `--migrate`）→ 校验受保护文件，改动/删除的从备份还原、新增的删除 → 按**上次的选项**重新 `apply`（没有记录则 `--all`）→ `doctor`。

| | 内容 |
|---|---|
| 逐字节保留 | `.trellis/spec/`、`tasks/`、`workspace/`、`.developer`、`.current-task`（上游也保护这五项）；加 `config.yaml`（`trellis update --force` 会重写它，所以由 `update` 校验并还原） |
| 直接覆盖 | Trellis 管理的其余文件（`.trellis/scripts/`、`agents/`、`workflow.md`、`.opencode/` 的 agents / lib 等）与 trellis-plus 随包文件（`gate.mjs`、模板、`plus-*`）。你自己新增、Trellis 不管理的文件不动 |
| 例外 | `.trellis/spec/` 内的随包指南（`plus-testing-guide.md` 等）：你改过就保留，新版写到 `*.plus-new`；`doctor` 对这种已知情况只提示不算故障 |
| 备份 | `.trellis/plus/backup/<时间>/`（trellis-plus 覆盖的文件 + 受保护文件的完整副本；受保护快照保留最近 3 份，更旧的备份目录也会清理）、`.trellis/.backup-<时间>/`（Trellis 覆盖的文件） |

`.trellis/plus/plus.config.json` 同样保留，但 `apply` 会更新其中 `version` 键为当前工具版本（其余键与排版不变）。

- 受保护文件被 Trellis 改动、删除或新增（`config.yaml` 被重写除外，那是已知行为，静默还原）：已还原/删除，**在 apply 之前停止**，退出码 1。
- `trellis update` 失败：受保护文件完好；排除原因后重跑 `update`（安全，可重复）或 `doctor --fix`。
- 项目的 Trellis 比 0.6.17 新：拒绝；`--allow-downgrade` 才退回。Trellis 版本变化（升级或降级）时，它的新 `config.yaml` 另存为 `.trellis/config.yaml.trellis-new`，请合并新增段落。

### 2.3 分步命令

```bash
node trellis-plus.mjs apply  <项目目录> --dry-run   # 先看会改什么
node trellis-plus.mjs apply  <项目目录> --all       # 硬门禁 + plugin 补丁 + agent 补丁 + git hook + AGENTS.md 编码规范
node trellis-plus.mjs status <项目目录>              # 激活任务的流程进度（--all 全部任务，--json 机读）
node trellis-plus.mjs doctor <项目目录> [--fix]     # 补丁是否被冲掉（update 已自动跑）
node trellis-plus.mjs revert <项目目录> [--purge]   # 还原补丁；--purge 同时删除随包文件
```

- `apply` 幂等；`plus.config.json` 属于项目，不会被覆盖。
- 自己手动跑 `trellis update` 会把被补丁的文件当作“你改过的”；之后跑 `doctor --fix`，或直接用 `trellis-plus update`。
- 安装后把 `.trellis/plus/` 与 `.opencode/` 的新增文件提交进仓库，队友直接用 `node .trellis/plus/gate.mjs …`。
- `doctor` 会提示非法的 `profile` / `gates` 配置，以及不是 `error` 的开关。

## 3. 日常流程

以下 `GATE` = `node ./.trellis/plus/gate.mjs`，`<T>` = 任务目录。

1. **创建任务并定级（AI 建议 → 用户选择）**：AI 先看代码（几个 Service/Controller、几个模块、有无库表/契约/事务变更），给出 S/M/L 建议与理由，在对话里请你选择；选定后执行 `GATE tier <T> S|M|L --reason "<理由；用户选 X>"`（S/M 必须写原因）。再 `GATE seed <T>` 生成模板。
2. **勘探（仅 L）**：用 trellis-research 写 `research/code-map.md`（锚点格式 `文件:行#符号`）。
3. **澄清**：建议在 OpenCode 里手动输入 `/grill-me`（没装或不想用就跳过，让 AI 直接向你提问；澄清前 AI 不会提前写 design/implement），结论写进 `prd.md` 的“决策记录”（确实没有可记的，写一行 `无：<原因>`），需求按功能分 `###` 小节、每条编号 `R<n>`，把“对齐状态”改为“已对齐”，待确认问题清零。运行 `GATE align <T>`。
4. **起草（M/L，建议新会话）**：加载 `plus-draft` 技能写 `design.md`、`implement.md`；运行 `GATE lint-plan <T>`，按提示修到通过。
5. **评审（仅 L，新会话）**：派发 `plus-design-reviewer`（最多 2 轮），在 `reviews/design-review-resolution.md` 逐条回应阻塞项（`- #3 采纳 — …` 或 `- #4 驳回 — <path:行 或 prd.md 出处>`），运行 `GATE design-review <T>`。需人工确认项 ≥ 3 时可用 `/plus-grill-design`。
6. **开始实现**：`task.py start` 会再次运行该级别的全部计划类门禁。
7. **实现与检查**：implement / check 子 agent 只做静态单测检查。
8. **单测门禁（2.4）**：`GATE test --task <T> --run`，每个被改的 Service/Controller 要有同模块、本次改过、含 `@Test` 的单测；`--run` 按模块执行 Maven。
9. **OCR（2.5）**：`GATE ocr --task <T> --run`。
   - 先 `ocr llm test`；可用则调用 ocr，报告保存为 `reviews/ocr-r<N>.json`。
   - 不可用则打印 **委托模式** 指引：由 agent 自己审查代码，写出同格式报告。
   - 把每条 finding 分诊写入 `reviews/ocr-triage.md`（`- [fixed|false-positive|deferred] 文件:行 — 说明`）。critical/high 不能 deferred，误报要引用存在的 `path:行`。同文件同行的多条 finding 要各写一行。
   - 只有上一轮含 critical/high 且已修复时才可重跑，最多 2 次修完 finding 后更新分诊即可，无需重跑；`--force` 越过上限须带 `--reason`，会记入 `reviews/ocr-overrides.log`，且必须先告知你。
   - 校验：`GATE ocr --task <T>`。
10. **提交**：`git commit` 时 hook 检查已暂存文件的单测与 OCR 分诊；没装 hook 才需先手工 `GATE pre-commit --task <T>`。

随时可用（0 token）：`GATE status <T>` 看下一步；`GATE usage <T> --phase <名> --tokens <n>` 记 token；`GATE matrix <T>` 打印 R→模块→测试矩阵；`GATE anchors <T>` 单独核对锚点；`GATE gates` 看开关。

### 3.1 Bug 修复（flow bugfix）

缺陷修复不分级、不写 `prd.md`、不跑 `align`：
1. `GATE flow <T> bugfix --from <原任务目录名>`，再 `GATE seed <T>` 生成 `bugfix.md` 并自动登记进 `implement.jsonl` / `check.jsonl`（加载 `plus-bugfix` 技能填写）。
2. 必须写清：根因（`文件:行#符号`）、**修复方案**（改什么、怎么改、为什么、什么不变）、允许改动文件、**回归测试 `类#方法`**（`task.py start` 前“修复前”列可填 `待先红验证`，无需提前改代码）。`GATE bug-plan <T>` 会前置检查规模与高风险（pom/SQL、>3 类或跨模块），通过后才能 `task.py start`。
3. 修复：进入编码后先写回归测试、确认先失败并把失败命令与摘要回填第 5 节，再改代码；**必须新增或修改单元测试**（改 Service/Controller 时优先写在对应的 `*Test.java`）。
4. `GATE test --task <T> --run`：除常规单测门禁外，执行 `bug-verify`：改了第 4 节没列的非测试文件时，默认 `scopeLock=confirm` 会**阻断并提示向用户确认**（同意后记入第 8 节“范围确认”或补进第 4 节即放行；`error` 仅认第 4 节）；同时核对回归测试在本次改动里、已填修复前失败证据、pom/SQL 有第 7 节处置。
5. 之后 OCR 分诊、提交与功能流程相同。超过 3 个 Service/Controller 或跨模块时，拆任务、改用 `GATE flow <T> feature` + L 级，或经用户确认后在第 7 节填写回滚/兼容方案并附 `用户确认`。

## 4. 文档模板要点

- **prd.md**：`对齐状态：已对齐|未对齐`；“需求与验收”下按功能 `### 名称`，每节一张表（编号 R1…、需求、验收标准）；决策记录表 `D<n>`（问题/结论/来源/影响）；待确认问题为空写“无”。
- **design.md**（M 可省第 2、8 节）：0 评审导读、1 背景与目标、2 术语、3 整体方案、**4 数据库变更**（表/变更类型/内容/兼容与回滚/对应R，或 `无变更：原因`）、**5 详细设计**（每个模块一个 `### 5.n 模块名`：接口表、关键逻辑伪代码树、只写改动字段的字段与口径；**没有单独的“模块拆分”章节**）、6 异常与边界、7 影响分析（引用数写“命令 → 命中数”，≥5 处须标“高风险”）、8 非功能、9 依赖/风险/回滚、10 覆盖矩阵与上线检查、11 开放问题。
- **implement.md**：`### 步骤 n：类名` 下只写“文件”（反引号路径，新增文件写“新增”）和“改什么”；测试矩阵（对应R/类/用例/类型，类型只写 正常/边界/异常）；测试豁免（无则写“无”）。
- 需求编号：`R1`、`R2`，或层级编号 `R1.1`、`R1.2`（整串是一个编号；写了 `R1.1` 时 `R1` 视为分组，design 里引用 `R1` 即覆盖其下全部）。列表写需求时，验收说明缩进写在需求下面，不会被当成需求项。
- 代码引用 `文件:行#符号`：**不要求全路径**，`OrderService.java:42#create` 或 `service/OrderService.java:42#create` 都可以，gate 在仓库里按后缀查找；文件、行号、符号仍会校验。同名文件多时只告警，并按候选文件逐个校验。implement.md 的文件路径同理。
- 体积只是提示：prd 10 KB、design M 12 KB / L 30 KB、implement 20 KB、三者合计 60 KB，超了只告警、不阻断。`research/code-map.md` 不限制大小（它不会注入子 agent）。

## 5. 配置 `.trellis/plus/plus.config.json`

只写要覆盖的键：

```json
{
  "profile": "standard",
  "gates": { "designReview": "warn" },
  "ocr": { "mode": "auto", "maxRerun": 2 },
  "testGate": { "methodLevel": "warn" },
  "hook": { "runTests": false }
}
```

| 键 | 说明 |
|---|---|
| `profile` | `standard`（默认）/ `strict`（另将 ocr.onIncomplete、methodLevel 提到 error）/ `light` |
| `gates.<名>` | `align lintPlan designReview manifests test ocr hook` → `error` / `warn` / `off` |
| `ocr.mode` | `auto`（先 `ocr llm test`，失败转委托模式）/ `cli`（仅 ocr，失败即错误）/ `delegate`（不调用 ocr） |
| `ocr.maxRerun` | 默认 2（首次不计） |
| `testGate.methodLevel` | 方法名近似检查：`warn`（默认）/ `error` / `off` |
| `testGate.runCommand` | 默认 `mvn -q -pl {module} -am test -Dtest={classes} -Dsurefire.failIfNoSpecifiedTests=false` |
| `limits.*`、`tiers.maxClassesM` | 体积提示线（仅告警）、M 级最多几个类 |

## 6. 退出码、任务选择与绕过

- 退出码：0 通过 / 1 门禁失败 / 2 用法或配置错误。
- 任务选择（hook、OCR）：`--task` > `TRELLIS_PLUS_TASK` > 会话任务 > **唯一**的 in_progress 任务（`00-bootstrap-*` 不计）；有多个且没有指定时不猜：hook 里 OCR 降为告警，命令行报错。
- 绕过（谨慎，并告知用户）：`TRELLIS_PLUS_SKIP_GATE=1 git commit …` 或 `git commit --no-verify`。

## 7. 常见问题

| 现象 | 处理 |
|---|---|
| `task has no tier` | AI 先给建议与理由，你选定后再 `GATE tier <T> S|M|L --reason "…"` |
| `WARN tier S/M is below the suggested …` | 只是提示：改动超出建议规模，级别仍按你的选择；hook 默认只提示（要拦提交设 `gates.hook = error`） |
| lint-plan 报占位符 | 把 `【填写：…】` 全部替换掉（包括伪代码块与表格里的） |
| lint-plan 报锚点失败 | 核对 `文件:行#符号` 是否真实存在（符号需在 ±15 行内） |
| OCR 提示 `DELEGATION MODE` | `ocr llm test` 失败或没装 ocr：按提示由 agent 自审并写 `ocr-r<N>.json` |
| OCR 报 `finding not triaged` | 每条 finding 需要一行分诊；同文件同行有两条就写两行 |
| OCR 报 `status partial` | 有文件没被审到：重跑或自己审那些文件 |
| `trellis update` 之后补丁丢了 | `node trellis-plus.mjs doctor <项目> --fix` |
| 配置写错后所有 gate 命令退出 2 | 看报错的键名，改 `plus.config.json`；`doctor` 也会提示 |

## 8. 未验证项（使用时请留意）

真实 ocr 的失败退出码与 `--audience agent` 下 stdout 的纯净度；critical 级别报告；委托模式的真实效果；真实 Maven 与你们父 pom 的 surefire 配置（`-Dtest` 会覆盖 `includes`，理论可行，未实测）；CodeGraph；`/grill-me`、评审 agent 在真实 OpenCode 中的表现；Windows。

## 全栈需求（前后端共用一个 PRD，design / implement 分开）

1. 父任务：`task.py create "<标题>"` → `GATE tier <父> M|L --reason …` → `GATE seed <父> --prd-only` → 澄清、写 prd.md → `GATE align <父>`。
2. 子任务：`task.py create "<标题> backend" --parent <父>`，再建 frontend。子任务不用再定级（继承父任务），也不用写 PRD（沿用父任务的 prd.md）。`GATE seed <子>` 生成它自己的 design.md、implement.md，并把父任务的 prd.md 写进它的 `implement.jsonl` / `check.jsonl`。
3. 每个子任务的“覆盖矩阵”只写自己负责的 R；`GATE lint-plan <子>` 会提示还没有任何子任务覆盖的 R（只告警）；`GATE matrix <父>` 汇总整个任务族。
4. 每个子任务单独走评审、单测门禁和 spec（前后端 spec 不同）。子任务如果自己写了完整的 prd.md（含“对齐状态”行），则用自己的，不继承。
