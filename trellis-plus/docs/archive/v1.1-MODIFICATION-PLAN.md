## 1. 项目背景与目标

### 1.1 用户的原始需求

用户使用 `mindfoldhq/trellis` + `opencode` 做开发工作流，技术栈 **Java 8 + Maven + JUnit5 + Mockito**。遇到四个问题：

1. task 生成的 `prd.md / design.md / implement.md` **颗粒度不够**，开发难以 review（推测原因：`workflow.md` 对 design/implement 描述抽象、缺少对代码探索深度的要求）。
2. **不强制**对每个修改的 service / controller 写单元测试。
3. 缺少用 **subagent 审查** `design.md / implement.md`（设计准确性、是否完全满足需求、关联影响分析）。
4. 缺少用 **alibaba/open-code-review（ocr）** 做 code review 的步骤。

约束：在 `trellis init` 之后执行一个 **Node.js 脚本**增强功能；脚本接收 **Trellis 项目路径参数**，不需要预先复制进项目。

### 1.2 v1 的解决思路（已实现）

一个**幂等**的安装器 `trellis-plus.mjs`（apply / doctor / revert），向项目写入：新 agent、新 skill、模板、门禁脚本 `gate.mjs`、规范文档；并用**标记块**补丁 `workflow.md`（新增步骤 1.6/1.7/2.4/2.5 + 在 `planning`/`in_progress` 面包屑里追加 `[plus] ` 行）；可选补丁 `task.py`（`task.py start` 硬门禁）、`trellis-context.js`（reviewer 不收面包屑）、`config.yaml`（上调注入上限）。

### 1.3 本轮（v1.1）目标

用户已确认：**P0 + P1 全做，P2 暂不做**。来源：把 v1 与另外三个社区项目（enhance-wb / enterprise-enhancer / team-kit）在同一 Trellis 0.6.17 副本、同一 Java 场景下做了对比，得出 v1 的 6 项差距：

| # | 级别 | 目标 | 一句话验收 |
|---|---|---|---|
| P0-1 | 必须 | **提交时硬兜底**：git pre-commit hook | AI 绕过 2.4/2.5 直接 `git commit`，缺测试/OCR 未分诊时提交被拦 |
| P0-2 | 必须 | **`--patch-agents`**：给 `trellis-implement`/`trellis-check` 加测试规范托管块 | 轻量任务里的实现子代理也被要求写单测 |
| P0-3 | 必须 | **轻量任务拦截** | 任务标 lightweight 但改了 Service/Controller → `test`/`pre-commit` 失败 |
| P1-4 | 重要 | **OCR 门禁增强**：版本检查 + severity 感知分诊 + 任务背景 | critical/high 不能 deferred；误报需代码证据；ocr<1.9.0 报错；`--run` 带 `--background-file` |
| P1-5 | 重要 | **设计模板与 reviewer 增强**：Java 专项章节、隐含假设检测、反向验收、高引用数风险 | 模板含数据模型/事务并发异常章节；reviewer 提示词含新检查 |
| P1-6 | 重要 | **稳定编号追溯链** `REQ→DES→IMP→TEST` | gate 校验整条链，缺任何一环都报具体错误 |

**不做（P2，留作后续）**：Maven 多模块按 `pom.xml` 定位模块运行测试；在步骤 1.1 加深度要求指针；`--install-ocr` 自动安装。

### 3.2 open-code-review（ocr）事实核查

来源：GitHub README、OpenCode 集成 README、`pi-open-code-review` 的 SKILL.md、delegate 技能文档的镜像页（supercode.sh / tessl.io）。官方 `open-codereview.ai/docs/cli-reference` 我访问时返回 404。

| 结论 | 状态 |
|---|---|
| `ocr review --format json --output result.json`（输出到**文件路径**）| 【文档】README 推荐用法 |
| `ocr review --audience agent`；工作区模式包含 staged/unstaged/untracked | 【文档】OpenCode 集成 README / Pi skill |
| `--from <base> --to <branch>`、`--commit` | 【文档】README |
| `-b/--background <text>`、`-B/--background-file <path>`，且**有两处独立的大小限制** | 【文档】delegate 文档；是否被 `review` 子命令接受、限制具体数值 **【未验证】** |
| `--format` 需要 ocr **≥ 1.9.0**，旧版报 `unknown flag` | 【文档】 |
| severity 枚举 `critical / high / medium / low` | 【文档】delegate 的 finding schema；review 输出是否一致 **【未验证】** |
| 需要 git ≥ 2.41；npm 包 `@alibaba-group/open-code-review` | 【文档】 |
| Delegation 模式（`ocr delegate preview/rule`）：用 coding agent 自己的模型做 review，无需 OCR API key | 【文档】 |
| **`review` 输出 JSON 的真实顶层结构**（`comments[]`？顶层数组？）、**退出码语义** | **【未验证】** → v1 用启发式识别；v1.1 加 `--inspect` 辅助适配（见 5.4）|

**enhance-wb（2069 行）**

- 【读码】校验靠子串；`file:line` 锚点只要出现 `:数字` 就算；设计审查无哈希绑定；OCR 分诊表有但**无代码强制**；整体替换 1.1/1.4/1.5 与面包屑，上游更新后会丢内容；`ensureFile` 文件存在就不再更新。
- **值得借鉴**：1.1 探索协议文案（四项强制）；`--check` CI 漂移检测；`--from/--to` 范围审查的用法。

**enterprise-enhancer（593 行）**
- 【实测】`validate-plan.mjs` 对**含新增文件路径的计划直接判失败**（`references a path that does not exist`）；去掉新增路径后，含 `:999` 行号和虚构方法 `placeOrderV2` 的设计**通过**。

## 4. 总体修改原则

1. **不退化**：每次改完先跑 `run-regression.sh`；格式变化导致的断言变化必须**同步更新夹具并在提交说明里写明**。
2. **不静默**：补丁锚点找不到就中止并报错（v1 行为），不要像 enterprise 那样 EOF 兜底或 wb 那样跳过。
3. **资源以文件形式存在**：Markdown/提示词放 `assets/`，**不要**在 JS 里拼接生成（wb 的反引号事故）。
4. **能确定性检查的不交给提示词**：只有无法机器判定的部分才写进 agent/skill。
5. **幂等 + 可还原**：新增的每个补丁（git hook、agent 托管块）都要有 apply / doctor / revert 三件套，并进回归（revert 后字节一致）。
6. **未验证的外部事实不要硬编码为真**：OCR JSON 结构用容错解析 + `--inspect`；参数不被识别时降级重试。

### 5.1 P0-1 提交时硬兜底（git pre-commit hook）

**目的**：2.4/2.5 目前全靠 AI 自觉；hook 是确定性的最后一道。

**安装器：`apply --git-hook`**

- 定位：`git -C ROOT rev-parse --git-path hooks`（兼容 worktree 与 `core.hooksPath`），相对路径要按 ROOT 解析；`git -C ROOT rev-parse --show-toplevel` 得 `top`，`rel = relative(top, ROOT)`（项目是仓库子目录时非空）。非 git 仓库 → 警告并跳过，不报错。
- 文件 `<hooks>/pre-commit`：
  - 不存在：创建 `#!/bin/sh\n` + 块，`chmod 755`，`manifest.options.hookCreated = true`。
  - 已存在：**先看 shebang**。仅当第一行是 `#!/bin/sh`、`#!/bin/bash`、`#!/usr/bin/env sh|bash` 之一（或没有 shebang）才插入；若是 python/node 等其他解释器，块的 sh 语法会破坏原脚本 → **警告并跳过**，提示用户手动在 hook 里调用 `node .trellis/plus/gate.mjs pre-commit --hook`。
  - 可插入时**保留原内容**。块插入位置：若第一行是 shebang，则**紧跟 shebang 之后**（不能追加到末尾——原脚本末尾常有 `exit 0`，块永远执行不到）；无 shebang 则放最前。
  - 块（幂等，靠标记识别）：
    ```sh
    # >>> trellis-plus >>>
    # Installed by trellis-plus. One-off bypass: TRELLIS_PLUS_SKIP_GATE=1 git commit …   (or git commit --no-verify)
    if [ -z "$TRELLIS_PLUS_SKIP_GATE" ] && command -v node >/dev/null 2>&1 && [ -f "<rel>/.trellis/plus/gate.mjs" ]; then
      node "<rel>/.trellis/plus/gate.mjs" pre-commit --hook || exit 1
    fi
    # <<< trellis-plus <<<
    ```
    `<rel>` 为空时写 `.trellis/plus/gate.mjs`；路径用 POSIX 斜杠。
- `revert`：删除块；若 `hookCreated` 且删后只剩 shebang/空行 → 删文件。`doctor`：块存在且 gate.mjs 存在；`--fix` 重装。
- 重复 `apply` 不能产生第二个块；块内容变化时就地替换。

**gate：`pre-commit --hook`**（在 `main` 的 `pre-commit` 分支）

```
if (env TRELLIS_PLUS_SKIP_GATE) exit 0
staged = changedFiles(_, true)
gateable = staged.some(f => isSource(f, cfg.ocr) || matchAny(cfg.testGate.include, f))
if (!gateable) { print "nothing to gate (no staged source files)"; exit 0 }      // 放行只含 .trellis/ 的记账提交
t = taskFromOpts(opts)                                                          // 会话 → in_progress 最新 → null
r1 = testGate(t, cfg, { staged: true })                                         // 不跑 --run（太慢）；可选 config.hook.runTests
reps = [r1]
if (cfg.ocr.enabled && cfg.ocr.required) {
  if (t) reps.push(ocrGate(t, cfg, { staged: true, run: false }))               // 只检查，不运行
  else r1.note("no in_progress task: OCR gate skipped")
}
print all; exit(any fail ? 1 : 0)
```

- 失败信息要**可操作**：缺测试→列出期望的测试路径；OCR 缺报告→给出 `node .trellis/plus/gate.mjs ocr --task <dir> --run`；并提示绕过方式。
- 输出走 stdout/stderr 均可（git 都会显示）。

**边界**：`git commit -a`、`git commit <paths>`（临时 index，见 5.0-1）；merge/rebase 提交（无 staged 源码则放行）；空提交；项目是仓库子目录；Windows 需 Git Bash（`sh`）。

### 5.3 P0-3 轻量任务拦截

**背景**：`gate lightweight` 只要求 `--reason ≥10 字`，AI 可单方面标轻量以躲开设计/审查/Test Matrix。采纳 team-kit 的判定规则，把其中**能确定性判断的部分**做成门禁。

### 5.4 P1-4 OCR 门禁增强

改动集中在 `ocrGate`（v1 L570）和 `countFindings`（L546）。

**(a) 版本检查**（仅 `--run`）：`ocr --version` 输出用 `/(\d+)\.(\d+)\.(\d+)/` 解析；低于 `ocr.minVersion`（默认 `1.9.0`）→ error：`ocr X is too old (--format needs >= 1.9.0). npm install -g @alibaba-group/open-code-review@latest`。无法解析 → warn 并继续。复用现有 `verGte`。

**(b) severity 感知分诊**

1. `extractFindings(json) → [{file, line, severity, message}]`：递归遍历，**同时含**文件键（`file|path|filename|file_path|filePath`）、行键（`line|start_line|startLine|line_number|lineNumber|range|position`）、消息键（`comment|message|content|description|title|issue|body|text`）的对象视为 finding（不再向其内部下降）。`line` 可能是数字/数字字符串/`{start|line}` 对象 → 归一为 number|null。severity 取 `severity|level|priority|risk`。
2. `normSeverity(s)`：`critical|blocker|fatal→critical`；`high|major|error→high`；`medium|moderate|warning|warn→medium`；`low|minor|info|suggestion|nit→low`；其他/缺失→`medium`（但仍要分诊）。
3. 分诊文件格式（更新 `plus-ocr-review` skill 的模板，**严重度写在方括号里便于人读**）：
   ```
   Report: ocr-r<N>.json
   Round: <N>

   - [fixed] path/File.java:42 — [high] NPE on dto — added null check in create()
   - [false-positive] path/File.java:88 — [critical] SQL injection — query is parameterized: src/main/resources/mapper/OrderMapper.xml:31
   - [deferred] path/File.java:12 — [low] naming — non-blocking; needs user decision
   ```
   解析正则：`^\s*[-*]\s*\[(fixed|false-positive|deferred|pending)\]\s+(\S+?)(?::(\d+))?\s+[—–-]\s+(.*)$` → `{status, file, line, note}`。
4. 匹配：对每个 finding 找 `basename(file)` 相同且（`line` 相等，或任一侧缺行号）的条目（允许一条覆盖同一行的多个 finding）。**报告里提取不到 file 的 finding** 退回 v1 的"条目数 ≥ finding 数"。
5. 规则：

   | finding severity | fixed | false-positive | deferred |
   |---|---|---|---|
   | 阻断（`blockingSeverities`，默认 critical/high）| ✔ | 备注必须含代码锚点 `path:line`（`/[\w./\\-]+\.\w+:\d+/`）| ✘ **不允许** |
   | 非阻断（medium/low/未知）| ✔ | 备注 ≥ 10 字符 | ✔，但汇总告警提示"需用户决策" |

   未匹配到条目 → error `finding not triaged: [high] File.java:8 <message前60字>`；有 `pending` → error。
6. 摘要 note：`findings: 2 (critical 0, high 1, medium 0, low 1)`。
7. **`gate ocr --inspect [--task t]`**：打印最近一份报告解析出的 finding 表（file/line/severity/message）和使用的键名。**这是应对"真实 JSON 结构未验证"的关键工具**：拿到真实输出后能一眼看出提取是否正确，再调 `extractFindings`。

**(c) 任务背景**（`--run` 时，`ocr.background=true`）

- 生成 `reviews/ocr-background.md`（**短摘要，≤ `backgroundMaxChars`，默认 6000**）：
  1. 任务标题/描述（`task.json`）；
  2. `prd.md` 中含 `REQ-\d+` 的行（≤20 行）；
  3. `design.md` 的 Change Inventory 表（≤30 行）；
  4. `implement.md` 的 Test Exemptions（若非 `None.`）；
  5. 评审指示 3 条：对照变更清单检查实现；指出清单之外的改动；重点关注事务/并发/异常处理。
  超限时按 4→3 的顺序裁剪，并在末尾写 `(truncated)`。
- 命令追加 `--background-file <绝对路径>`。**降级**：`ocr` 以非 0 退出且 stderr 匹配 `/unknown (flag|shorthand)|flag provided but not defined|unrecognized/i` 且含 `background` → 去掉该参数**重试一次**并 warn（v1.1 需把 `spawnSync` 改为 `stdio:["inherit","inherit","pipe"]` 以捕获并回显 stderr）。
- 不要把整份 prd/design/implement 拼进去（文档越细越容易超 ocr 的大小限制）。

**测试（J 组，用 `fixtures/ocr/*.json` + 假 ocr）**

| ID | 场景 | 期望 |
|---|---|---|
| J1 | `FAKE_OCR_VERSION=1.8.0 … --run` | 失败并提示升级 |
| J2 | high 的 finding 标 `[deferred]` | 失败：blocking 不可 deferred |
| J3 | critical 标 `[false-positive]` 但备注无 `path:line` | 失败：需要代码证据 |
| J4 | 同上备注含 `OrderMapper.xml:31` | 通过 |

## 7. 风险、未验证事项与注意坑

**外部事实未验证**
- ocr 的真实 JSON 结构、退出码、`--background-file` 对 `review` 的支持与大小限制 → 用 `--inspect` 与降级重试兜底；**拿到真实样例后回头改 `extractFindings` 并替换 `fixtures/ocr`**。
- OpenCode agent frontmatter 的 `model` 字段、`permission.edit` 路径级限制 → 未验证；reviewer 目前靠提示词约束只写 `reviews/`。
- 没有真实 OpenCode + LLM 环境，**软门禁（提示词）AI 是否遵守无法验证**；硬门禁只有 `task.py start` 与（本轮新增的）git hook。
- Windows 未验证（hook 依赖 `sh`/Git Bash；ocr 调用不用 `sh -lc`）。
- Trellis 自动提交行为未核实（见 3.1 末尾），影响 hook 的放行规则。

**实现注意**
- **`node --check` 不可靠**：wb 的坏插件它放行了。凡涉及生成 JS 的补丁都用 `smoke_load.mjs` 真实 import。
- **沙箱 shell 是 dash**：`mkdir -p a/{b,c}` 会建出名字含花括号的目录；`<(…)`、`${PIPESTATUS[0]}` 报 `Bad substitution`/语法错误。写测试一律 `bash`。（本项目开发中三次踩到。）
- 面包屑块内**不能放 HTML 注释**（每轮会被注入，且污染 token）；用 `[plus] ` 行作哨兵，幂等靠"先删所有 `[plus] ` 行再重写"。
- `get_step` 编号约束（F2）；`[plus]` 行必须有正文（F3）。
- 补丁锚点缺失 → **中止并报错**，不要兜底写到文件末尾。
- 新增受管文件用 manifest 哈希保护本地修改；被改过的写 `.plus-new`，不要静默覆盖。
- hook 里**不要清理 `GIT_INDEX_FILE` 等 git 注入的环境变量**。
- `--all` 现在会安装 git hook，属于**对用户仓库 `.git/` 的改动**，README 要醒目说明，并保证 `revert` 能干净移除。
- 提交时 hook 失败会打断 AI 的提交流程：失败信息必须给出明确的修复命令，避免 AI 陷入循环；循环风险点：OCR 对 critical 误报——所以才有"误报+代码锚点"通道。
